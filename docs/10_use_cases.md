# 10. Варианты использования системы

## 1. Назначение

Документ описывает варианты использования текущего прототипа «1С Service Desk». Он связывает пользовательские действия с реализованными статусами, проверками и объектами конфигурации.

Диаграмма Use Case будет добавлена отдельно после согласования сценариев этого документа.

## 2. Акторы

| Актор | Ответственность |
|---|---|
| Сотрудник | Создаёт заявку и предоставляет сведения по своей проблеме |
| Исполнитель заявки | Обрабатывает назначенную заявку, запрашивает уточнение и фиксирует решение |
| Руководитель IT-отдела | Назначает исполнителей, контролирует заявки и SLA |
| Ответственный за оборудование | Ведёт оборудование и выполняет связанные с ним операции |
| Администратор системы | Настраивает справочники, пользователей, роли и правила SLA |
| Клиент HTTP API | Создаёт и получает заявки от имени авторизованного пользователя 1С |

Технические права задаются ролями конфигурации. Название отдельной технической роли обычного сотрудника в этом документе не фиксируется, поскольку его необходимо сверить с конфигурацией.

## 3. Состояния заявки

В текущей реализации используются следующие статусы:

1. «Новая»;
2. «Назначена»;
3. «В работе»;
4. «Ожидает уточнения»;
5. «Ожидает оборудование»;
6. «Решена»;
7. «Закрыта»;
8. «Отменена».

«Просрочена» не является статусом заявки. Нарушения сроков реакции и решения фиксируются отдельно в регистре сведений «НарушенияSLA».

## 5. UC-01. Создать IT-заявку

**Цель:** зарегистрировать обращение сотрудника.

**Предусловия:**

- пользователь авторизован;
- пользователь информационной базы связан с активным сотрудником;
- в системе существуют категория и приоритет.

**Основной сценарий:**

1. Пользователь создаёт заявку через интерфейс 1С или HTTP API.
2. Указывает категорию, приоритет и описание проблемы.
3. При необходимости указывает оборудование.
4. Система проверяет обязательные поля.
5. Если категория требует оборудование, система проверяет его заполнение.
6. Система создаёт документ с начальным статусом «Новая».
7. Система рассчитывает сроки реакции и решения по правилу SLA.

**Альтернативы:**

- при отсутствии обязательного поля заявка не записывается;
- если для категории требуется оборудование, а оно не указано, заявка не записывается;
- если правило SLA не найдено или содержит некорректные сроки, запись заявки отклоняется;
- HTTP API возвращает ошибку, если текущему пользователю 1С не соответствует активный сотрудник.

**Результат:** создана заявка со статусом «Новая», рассчитанными сроками SLA и пустым исполнителем.

## 6. UC-02. Назначить исполнителя

**Цель:** определить ответственного за обработку заявки.

**Предусловия:**

- заявка находится в статусе «Новая»;
- выбранный сотрудник активен;
- сотрудник может быть исполнителем заявки.

**Основной сценарий:**

1. Руководитель открывает заявку.
2. Выбирает исполнителя.
3. Переводит заявку в статус «Назначена».
4. Система проверяет исполнителя и допустимость перехода.
5. Система сохраняет заявку и фиксирует изменение статуса.

**Результат:** заявка находится в статусе «Назначена» и имеет исполнителя.

## 7. UC-03. Взять заявку в работу

**Цель:** зафиксировать начало обработки заявки.

**Предусловия:**

- заявка находится в статусе «Назначена»;
- текущий сотрудник назначен исполнителем.

**Основной сценарий:**

1. Исполнитель открывает назначенную заявку.
2. Переводит её в статус «В работе».
3. Система проверяет допустимость перехода.
4. Система сохраняет заявку и запись истории статусов.

**Результат:** заявка находится в статусе «В работе». Время перехода используется при оценке соблюдения срока реакции.

## 8. UC-04. Запросить уточнение

**Цель:** получить недостающие сведения от заявителя.

**Предусловия:**

- заявка находится в статусе «В работе»;
- действие выполняет назначенный исполнитель.

**Основной сценарий:**

1. Исполнитель добавляет комментарий типа «Запрос уточнения».
2. Переводит заявку в статус «Ожидает уточнения».
3. Система проверяет наличие обязательного комментария.
4. Система сохраняет изменение статуса.

**Результат:** заявка ожидает информацию от сотрудника.

## 9. UC-05. Предоставить уточнение

**Цель:** передать исполнителю недостающие сведения.

**Предусловия:** заявка находится в статусе «Ожидает уточнения».

**Основной сценарий:**

1. Сотрудник добавляет комментарий типа «Ответ сотрудника».
2. Заявка переводится обратно в статус «В работе».
3. Система проверяет наличие обязательного комментария.
4. Система фиксирует переход статуса.

**Результат:** обработка заявки продолжена.

## 10. UC-06. Перевести заявку в ожидание оборудования

**Цель:** приостановить решение до выполнения действия с оборудованием.

**Предусловия:**

- заявка находится в статусе «В работе»;
- с заявкой связано оборудование;
- действие выполняет назначенный исполнитель.

**Основной сценарий:**

1. Исполнитель переводит заявку в статус «Ожидает оборудование».
2. Система проверяет допустимость перехода.
3. Система фиксирует изменение статуса.

**Результат:** заявка находится в статусе «Ожидает оборудование».

## 11. UC-07. Возобновить работу после операции с оборудованием

**Цель:** продолжить обработку после завершения необходимой операции.

**Предусловия:**

- заявка находится в статусе «Ожидает оборудование»;
- связанная операция с оборудованием завершена.

**Основной сценарий:**

1. Исполнитель переводит заявку в статус «В работе».
2. Система проверяет факт завершения операции с оборудованием.
3. Система сохраняет переход.

**Результат:** обработка заявки продолжена.

## 12. UC-08. Зафиксировать решение заявки

**Цель:** завершить работу исполнителя и сохранить результат.

**Предусловия:**

- заявка находится в статусе «В работе»;
- действие выполняет назначенный исполнитель.

**Основной сценарий:**

1. Исполнитель заполняет результат выполнения.
2. Переводит заявку в статус «Решена».
3. Система проверяет заполнение результата и допустимость перехода.
4. Система фиксирует изменение статуса.

**Результат:** заявка находится в статусе «Решена». Время перехода используется при оценке соблюдения срока решения.

## 13. UC-09. Закрыть решённую заявку

**Цель:** завершить жизненный цикл заявки.

**Предусловия:** заявка находится в статусе «Решена».

**Основной сценарий:**

1. Руководитель IT-отдела или администратор проверяет результат.
2. Переводит заявку в статус «Закрыта».
3. Система фиксирует конечный статус.

**Результат:** заявка закрыта; дальнейшие переходы запрещены.

## 14. UC-10. Вернуть решённую заявку в работу

**Цель:** продолжить обработку, если решение требует доработки.

**Предусловия:** заявка находится в статусе «Решена».

**Основной сценарий:**

1. Руководитель IT-отдела или администратор добавляет комментарий типа «Причина возврата».
2. Переводит заявку в статус «В работе».
3. Система проверяет наличие причины возврата.
4. Система фиксирует переход.

**Результат:** заявка снова находится в работе.

## 15. UC-11. Отменить заявку

**Цель:** прекратить обработку заявки без решения.

**Предусловия:** текущий статус допускает переход в «Отменена».

**Основной сценарий:**

1. Пользователь с разрешённой ролью выбирает отмену.
2. Пользователь очищает исполнителя, если он был заполнен.
3. Система проверяет, что для отменённой заявки исполнитель не указан, затем сохраняет заявку.

**Результат:** заявка находится в конечном статусе «Отменена».

Точный перечень ролей, которым разрешена отмена на каждом этапе, необходимо дополнительно сверить с модулем объекта и ролями конфигурации.

## 16. UC-12. Контролировать SLA и анализировать заявки

**Цель:** контролировать сроки и работу IT-службы.

**Основной сценарий:**

1. Руководитель формирует отчёт «Контроль SLA» или «Анализ заявок».
2. Указывает период и необходимые отборы.
3. Система получает данные заявок, истории статусов и нарушений SLA.
4. Отчёт показывает результаты обработки и соблюдения сроков.

**Результат:** руководитель получает данные для контроля заявок и исполнителей.

## 17. UC-13. Вести оборудование

**Цель:** поддерживать актуальные сведения об оборудовании.

**Основной актор:** ответственный за оборудование.

Вариант использования включает просмотр и изменение карточек оборудования, закрепление оборудования и фиксацию операций, связанных с заявками. Точный состав документов и разрешённых операций должен соответствовать объектам текущей конфигурации.

## 18. UC-14. Настраивать систему

**Цель:** поддерживать работу Service Desk.

**Основной актор:** администратор.

Вариант использования включает настройку справочников, пользователей, ролей и правил SLA. Администратор не должен использовать технические права для подмены обычных действий участников процесса без служебной необходимости.

## 20. Зафиксированное расхождение

Первоначальная Use Case диаграмма относит закрытие и возврат решённой заявки к сотруднику. В проверенной логике модуля эти переходы выполняют руководитель IT-отдела или администратор. До изменения диаграммы и требований в документации фиксируется фактически реализованный вариант.

Если бизнес-требование предполагает подтверждение решения самим заявителем, потребуется отдельное изменение программной логики и повторное тестирование.
