# 16. Загрузка конфигурации из исходников

## 1. Что находится в `src`

Каталог `src` содержит выгрузку конфигурации 1С в файлы: корневой `Configuration.xml`, `ConfigDumpInfo.xml`, XML-описания объектов, модули BSL, формы и макеты СКД.

Это не готовая информационная база. Пользователи, элементы справочников, правила SLA, заявки и остальные данные в выгрузку конфигурации не входят.

## 2. Требования

- установленная платформа «1С:Предприятие 8.3» с поддержкой режима совместимости `Version8_3_27`;
- доступ к режиму «Конфигуратор»;
- новая пустая информационная база либо резервная копия базы, в которую выполняется загрузка;
- локальная копия репозитория.

Точный номер сборки платформы, на которой выгрузка была создана и проверена, в репозитории не зафиксирован. Режим совместимости подтверждается файлом `src/Configuration.xml`.

## 3. Получение репозитория

```powershell
git clone https://github.com/olyamyalina/1c-service-desk-analysis.git
cd 1c-service-desk-analysis
```

Если изменения ещё находятся в отдельной ветке, перед загрузкой переключиться на неё:

```powershell
git switch feat/add-1c-source
git pull
```

## 4. Загрузка в пустую базу

1. Создать новую файловую информационную базу без конфигурации.
2. Открыть её в режиме «Конфигуратор».
3. Если дерево конфигурации закрыто, выполнить `Конфигурация` → `Открыть конфигурацию`.
4. Выполнить `Конфигурация` → `Загрузить конфигурацию из файлов...`.
5. Выбрать каталог `src`, в котором находится `Configuration.xml`.
6. Дождаться завершения загрузки.
7. Выполнить `Конфигурация` → `Обновить конфигурацию базы данных`.
8. Подтвердить создание и изменение объектов базы данных.
9. Запустить базу в режиме «1С:Предприятие».

Загрузка заменяет конфигурацию выбранной базы. Для непустой базы перед операцией требуется резервная копия.

## 5. Первичная настройка

### 5.1. Пользователи и сотрудники

Для каждого прикладного пользователя:

1. создать пользователя информационной базы;
2. назначить `БазовыеПраваServiceDesk`;
3. назначить одну или несколько функциональных ролей:
   - `ПользовательСотрудник`;
   - `ИсполнительЗаявок`;
   - `РуководительITОтдела`;
   - `ОтветственныйЗаОборудование`;
   - `АдминистраторСистемы`;
4. создать элемент справочника `Сотрудники`;
5. в реквизите `ИмяПользователяИБ` указать точное имя пользователя информационной базы;
6. установить `Активен` и необходимые признаки: возможность быть исполнителем, руководитель IT-отдела или ответственный за оборудование.

Одному имени пользователя должен соответствовать ровно один активный сотрудник. Иначе прикладная логика не сможет однозначно определить текущего пользователя.

### 5.2. Нормативно-справочная информация

Создать:

- подразделения;
- категории заявок и при необходимости включить `ТребуетОборудование`;
- приоритеты заявок;
- типы оборудования;
- карточки оборудования.

Для HTTP API в справочнике приоритетов должны существовать элементы `Низкий`, `Средний` и `Высокий`, если именно эти значения используются клиентом.

### 5.3. Правила SLA

В периодическом регистре `ПравилаSLA` создать действующую запись для каждого используемого приоритета:

- период записи должен быть не позже даты создаваемой заявки;
- `СрокРеакцииЧасы` должен быть больше нуля;
- `СрокРешенияЧасы` должен быть больше нуля.

Категория не входит в ключ текущего регистра. Правило выбирается только по приоритету и дате заявки.

### 5.4. Оборудование

Для новой карточки без записей истории система возвращает состояние `НаСкладе`. Выдача сотруднику и изменение состояния выполняются документами `ЗакреплениеОборудования` и `РемонтОборудования`, которые создают записи в `ИсторияСостоянийОборудования`.

Реквизиты состояния и ответственного в карточке доступны только для чтения. Актуальные значения в списках формируются по последнему срезу регистра.

## 6. Минимальная проверка после загрузки

1. Войти пользователем с ролями `БазовыеПраваServiceDesk` и `ПользовательСотрудник`.
2. Создать заявку по категории, не требующей оборудование.
3. Проверить статус `Новая` и рассчитанные сроки SLA.
4. Войти руководителем, назначить исполнителя и перевести заявку в `Назначена`.
5. Войти назначенным исполнителем и перевести заявку в `ВРаботе`.
6. Проверить записи истории статусов, назначений и уведомлений.
7. Сформировать отчёт `АнализЗаявок`.

Полный прогон описан в [тестовых сценариях](14_test_scenarios.md).

## 7. Публикация HTTP-сервиса

Параметры веб-сервера и публикации информационной базы не хранятся в репозитории. После публикации базы с именем `ServiceDesk` стандартный локальный адрес из документации имеет вид:

```text
http://localhost/ServiceDesk/hs/api/v1
```

Доступные маршруты:

- `GET /ping`;
- `GET /tickets/{number}`;
- `POST /tickets`.

Запрос выполняется от имени пользователя 1С, имеющего право на соответствующий метод HTTP-сервиса. Для `POST /tickets` пользователь дополнительно должен быть связан ровно с одним активным сотрудником; именно он становится заявителем. Обработчики `GET` и `ping` такую связь не проверяют. Примеры приведены в [описании API](15_http_api.md).

HTTP без TLS и `localhost` подходят только для локальной учебной среды.

## 8. Обновление выгрузки после доработки

После изменения конфигурации в Конфигураторе:

1. выполнить `Конфигурация` → `Выгрузить конфигурацию в файлы...`;
2. выбрать существующий каталог `src`;
3. дождаться завершения выгрузки;
4. проверить изменения:

```powershell
git status
git diff --stat
git diff --check
```

5. убедиться, что в коммит не попали `.dt`, `.cf`, `.1CD`, файлы публикации и учётные данные;
6. обновить документацию, если изменились объекты, бизнес-логика или результаты тестов.

XML-файлы метаданных лучше изменять через Конфигуратор и повторную выгрузку, чтобы не нарушить служебные идентификаторы и структуру `ConfigDumpInfo.xml`.
