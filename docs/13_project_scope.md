# 13. Границы и статус проекта

## 1. Назначение

Документ отделяет целевую аналитическую модель от фактически выгруженной реализации. Источником сведений о реализации является каталог `src`; результаты ручной проверки фиксируются отдельно и не выводятся только из наличия кода.

## 2. Реализовано в исходниках

| Функциональный блок | Подтверждение в конфигурации |
|---|---|
| Создание и обработка IT-заявок | Документ `ITЗаявка`, модуль объекта и управляемые формы |
| Статусная модель и ролевые переходы | Перечисление `СтатусыЗаявок`, проверки в модуле `ITЗаявка` |
| История статусов и назначений | Регистры `ИсторияИзмененияСтатусов` и `НазначенияИсполнителей` |
| Комментарии и обязательные пояснения | Регистр `КомментарииЗаявок`, модуль `УправлениеКомментариямиСервер` |
| Расчёт и контроль SLA | `ПравилаSLA`, `НарушенияSLA`, `УправлениеSLAСервер`, регламентное задание |
| Уведомления | `УведомленияПользователей`, два общих модуля уведомлений, модуль приложения |
| Учёт оборудования | Справочники оборудования, документы выдачи и ремонта, `ИсторияСостоянийОборудования` |
| Списание оборудования | Значение `Списано` и запись выбранного состояния при завершении ремонта |
| Отчётность | Отчёты `АнализЗаявок` и `КонтрольSLA` |
| HTTP-интеграция | `ServiceDeskAPI` с тремя обработчиками: ping, получение и создание заявки |
| Роли | Базовая и пять функциональных ролей |

## 3. Подтверждено ручной проверкой

На текущий момент в документации зафиксированы два выполненных HTTP-сценария:

- успешный `POST /tickets`, создавший заявку №000000018;
- `POST /tickets` с пустым телом, вернувший HTTP 400 и сообщение `Тело запроса не заполнено.`

Эти результаты взяты из [документации HTTP API](15_http_api.md). Для остальных функций наличие обработчика или проверки в BSL подтверждает реализацию в исходниках, но не заменяет запуск теста в 1С.

## 4. Подготовлено, но ещё не подтверждено полным прогоном

- загрузка выгрузки `src` в новую пустую информационную базу;
- полный ролевой прогон жизненного цикла заявки;
- успешный и негативные сценарии `GET /tickets/{number}`;
- все негативные сценарии `POST /tickets`, кроме пустого тела;
- регламентный запуск проверки SLA;
- формирование обоих отчётов на полном наборе тестовых данных;
- сценарий ремонта со значением `Списано` и последующей выдачей замены;
- работа уведомлений для всех получателей и аннулирование комментариев.

Полный перечень проверок приведён в [тестовых сценариях](14_test_scenarios.md).

## 5. Известные ограничения текущей выгрузки

### 5.1. Отчёт `КонтрольSLA`

Объект отчёта включён в конфигурацию и подсистему `SLA`, однако в выгруженных правах роли `РуководительITОтдела` явно предоставлены права только на `АнализЗаявок`. Поэтому доступ руководителя к `КонтрольSLA` нельзя считать завершённым до добавления права и ручной проверки. Администратор получает права на новые объекты по умолчанию.

### 5.2. Отмена заявки

Модуль разрешает переход в `Отменена` руководителю IT-отдела или администратору, но не требует очистить исполнителя. Правило «у отменённой заявки исполнитель пуст» в текущем коде не обеспечено и не описывается как реализованное.

### 5.3. Ограничение видимости данных

Отбор своих и назначенных заявок настроен в форме списка. Это не полноценное ограничение доступа к строкам на уровне записей, поэтому доступ через другие интерфейсы должен проверяться отдельно. Для учебного прототипа используется прикладной контроль в формах и модулях.

### 5.4. SLA

Правило SLA зависит только от приоритета и даты заявки. Категория не входит в ключ регистра `ПравилаSLA`. Сроки считаются в календарных часах; производственный календарь, рабочее время и приостановка отсчёта на статусах ожидания отсутствуют.

Типы уведомлений о нарушении срока реакции и решения определены, но процедура регистрации нарушения не создаёт такие уведомления. Модуль содержит только обработку уже существующих уведомлений этого типа, поэтому автоматическое оповещение о новом нарушении требует доработки.

### 5.5. Оборудование

Операционным источником текущего состояния является `ИсторияСостоянийОборудования`. Реквизиты `ТекущееСостояние` и `ОтветственныйСотрудник` карточки оборудования доступны только для чтения, а списки получают актуальные значения через `СрезПоследних` регистра.

После завершения ремонта со значением `Списано` заявка не может вернуться в `ВРаботе` только на основании этой записи: проверка завершённой операции ищет состояние `Используется`. Для продолжения предусмотрена выдача замены по той же заявке.

### 5.6. HTTP API

Не реализованы получение списка заявок, изменение заявки и удаление заявки. Единый JSON-формат применяется к ошибкам, сформированным обработчиками 1С; ошибки веб-сервера или аутентификации могут иметь другой формат. Публикация `localhost` по HTTP предназначена только для локального обучения.

### 5.7. Тестирование и поставка

Автоматизированного набора тестов в репозитории нет. Файл информационной базы, данные пользователей, тестовые данные, публикация веб-сервера и бинарные поставки `.dt`/`.cf` не включены.

## 6. Вне текущей версии

Следующие возможности могут встречаться в документах требований как целевые, но отсутствуют в текущей выгрузке:

- объекты 1С `БизнесПроцесс` и `Задача`;
- регистры накопления;
- почтовые, мессенджерные и корпоративные интеграции;
- вложения к заявкам;
- база знаний и каталог типовых решений;
- рабочие календари и пауза SLA;
- автоматизированные тесты и CI;
- `GET /tickets`, `PATCH`/`PUT` и `DELETE` для заявок;
- мобильный клиент как отдельный проверенный сценарий.

## 7. Правило актуализации

После изменения конфигурации необходимо:

1. повторно выгрузить исходники в `src`;
2. проверить изменения через `git diff`;
3. обновить этот документ, архитектуру и тестовые сценарии;
4. переносить сценарий в статус «Проверено» только после фактического запуска и фиксации результата.
