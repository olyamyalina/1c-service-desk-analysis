# 12. Модель объектов 1С

## 1. Назначение

Документ описывает объекты, подтверждённые в текущем учебном прототипе «1С Service Desk», и их роль в системе.

Описание составлено по реализованной бизнес-логике, проверенным фрагментам модулей и результатам работы конфигурации. Полная выгрузка метаданных пока не размещена в репозитории, поэтому неподтверждённые технические реквизиты здесь не приводятся.

## 2. Общая структура

| Тип объекта | Подтверждённые объекты |
|---|---|
| Справочники | «Подразделения», «Сотрудники», «КатегорииЗаявок», «ПриоритетыЗаявок», «ТипыОборудования», «Оборудование» |
| Перечисления | «СтатусыЗаявок», «ТипыНарушенийSLA», «ТипыКомментариев», «ТипыУведомлений», «СостоянияОборудования» |
| Документы | «ITЗаявка», объекты операций с оборудованием |
| Регистры сведений | «ПравилаSLA», «ИсторияИзмененияСтатусов», «НазначенияИсполнителей», «НарушенияSLA», «КомментарииЗаявок», «УведомленияПользователей» |
| Отчёты | «Анализ заявок», «Контроль SLA» |
| HTTP-сервисы | «ServiceDeskAPI» |
| Роли | «ИсполнительЗаявок», «РуководительITОтдела», «ОтветственныйЗаОборудование», «АдминистраторСистемы» |

Точное техническое имя роли обычного сотрудника и полный состав объектов операций с оборудованием необходимо подтвердить по выгрузке конфигурации.

Регистры накопления, бизнес-процессы и задачи не включены в фактическую модель: их наличие в текущей конфигурации не подтверждено.

## 3. Справочники

### 3.1. «Подразделения»

Хранит организационные подразделения сотрудников. Полный перечень реквизитов будет зафиксирован после выгрузки метаданных.

### 3.2. «Сотрудники»

Хранит заявителей, исполнителей, руководителей и ответственных за оборудование.

| Подтверждённый реквизит | Назначение |
|---|---|
| `ИмяПользователяИБ` | Связь сотрудника с пользователем информационной базы |
| `Активен` | Возможность использовать сотрудника в действующих операциях |
| `МожетБытьИсполнителем` | Возможность назначить сотрудника исполнителем заявки |

Функция определения текущего сотрудника получает пользователя ИБ, ищет по его имени одного активного сотрудника и возвращает его ссылку. Отсутствие соответствия и несколько активных соответствий обрабатываются как ошибки. Эта связь используется HTTP API для определения заявителя без передачи `applicantCode`.

### 3.3. «КатегорииЗаявок»

Классифицирует обращения. Признак `ТребуетОборудование` делает оборудование обязательным для соответствующей категории. Категория участвует в подборе правила SLA вместе с приоритетом.

### 3.4. «ПриоритетыЗаявок»

В текущей реализации приоритет является справочником. Подтверждённые используемые наименования: «Низкий», «Средний», «Высокий».

Приоритет «Критический» не включён: его наличие в текущем справочнике и обработка в HTTP API не подтверждены.

### 3.5. «ТипыОборудования» и «Оборудование»

Первый справочник классифицирует устройства. Второй хранит единицы оборудования, их состояние и ответственного сотрудника. Оборудование может быть связано с IT-заявкой. Точные технические имена всех реквизитов должны быть получены из выгрузки конфигурации.

## 4. Перечисления

### 4.1. «СтатусыЗаявок»

Содержит восемь значений: `Новая`, `Назначена`, `ВРаботе`, `ОжидаетУточнения`, `ОжидаетОборудование`, `Решена`, `Закрыта`, `Отменена`.

Статус «Просрочена» отсутствует. Просрочка учитывается как нарушение SLA.

### 4.2. «ТипыНарушенийSLA»

Подтверждённые значения: `НарушениеСрокаРеакции` и `НарушениеСрокаРешения`.

### 4.3. «ТипыКомментариев»

Подтверждённые типы, участвующие в проверках переходов: `ЗапросУточнения`, `ОтветСотрудника`, `ПричинаВозврата`. Полный список необходимо сверить по метаданным.

### 4.4. Другие перечисления

«ТипыУведомлений» используется регистром уведомлений, а «СостоянияОборудования» — подсистемой оборудования. Полные списки значений необходимо сверить по метаданным.

## 5. Документ «ITЗаявка»

Документ является центральным объектом системы и хранит текущее состояние обращения.

| Подтверждённый реквизит | Назначение |
|---|---|
| `Дата` | Дата и время регистрации |
| `Заявитель` | Сотрудник, для которого создана заявка |
| `Категория` | Категория обращения |
| `Приоритет` | Приоритет заявки |
| `ОписаниеПроблемы` | Описание обращения |
| `Оборудование` | Связанная единица оборудования |
| `Исполнитель` | Назначенный исполнитель |
| `ТекущийСтатус` | Текущее состояние жизненного цикла |
| `СрокРеакции` | Рассчитанный срок реакции |
| `СрокРешения` | Рассчитанный срок решения |
| `РезультатВыполнения` | Результат решения |

При записи проверяются обязательные поля, оборудование для соответствующей категории, допустимость перехода, исполнитель, результат решения, обязательные комментарии и завершение операции с оборудованием. Для новой заявки исполнитель не указывается; в отменённой заявке он должен быть пустым.

### 5.1. Жизненный цикл

| Исходный статус | Допустимый следующий статус |
|---|---|
| Начальное состояние | Новая |
| Новая | Назначена, Отменена |
| Назначена | В работе, Отменена |
| В работе | Ожидает уточнения, Ожидает оборудование, Решена, Отменена |
| Ожидает уточнения | В работе, Отменена |
| Ожидает оборудование | В работе, Отменена |
| Решена | Закрыта, В работе |
| Закрыта | Переходы отсутствуют |
| Отменена | Переходы отсутствуют |

## 6. Регистры сведений

### 6.1. «ПравилаSLA»

Измерения: `Приоритет`, `Категория`. Ресурсы: `СрокРеакцииЧасы`, `СрокРешенияЧасы`.

Правило выбирается срезом последних на дату заявки по приоритету и категории. Сроки рассчитываются от даты заявки:

```text
СрокРеакции = ДатаЗаявки + СрокРеакцииЧасы × 3600
СрокРешения = ДатаЗаявки + СрокРешенияЧасы × 3600
```

Оба значения длительности должны быть больше нуля.

### 6.2. «ИсторияИзмененияСтатусов»

Фиксирует период изменения, заявку, старый статус, новый статус и пользователя. Комментарии хранятся отдельно.

### 6.3. «НазначенияИсполнителей»

Хранит историю назначения исполнителей. Точную структуру необходимо подтвердить по метаданным.

### 6.4. «НарушенияSLA»

Хранит заявку, тип нарушения и дату нарушения.

### 6.5. «КомментарииЗаявок»

Хранит комментарии отдельно от документа и истории статусов.

| Переход | Обязательный тип комментария |
|---|---|
| В работе → Ожидает уточнения | `ЗапросУточнения` |
| Ожидает уточнения → В работе | `ОтветСотрудника` |
| Решена → В работе | `ПричинаВозврата` |

### 6.6. «УведомленияПользователей»

Хранит уведомления сотрудников о событиях по заявкам. Получателем является сотрудник.

## 7. Отчёты

| Подтверждённый отчёт | Назначение |
|---|---|
| «Анализ заявок» | Анализ количества и состава заявок |
| «Контроль SLA» | Сопоставление плановых и фактических сроков реакции и решения |

Перечень из отдельных отчётов «Просроченные заявки», «Нарушения SLA», «Загрузка специалистов» и других не приводится как реализованный: их наличие не подтверждено.

## 8. HTTP-сервис «ServiceDeskAPI»

Подтверждены методы `GET /v1/ping`, `GET /v1/tickets/{number}` и `POST /v1/tickets`.

Сервис определяет заявителя по текущему пользователю ИБ и создаёт документ «ITЗаявка» с использованием тех же справочников и правил SLA. Подробный контракт описан в [документации HTTP API](15_http_api.md).

## 9. Роли

Подтверждённые технические роли: `ИсполнительЗаявок`, `РуководительITОтдела`, `ОтветственныйЗаОборудование`, `АдминистраторСистемы`.

Точное имя роли обычного сотрудника необходимо подтвердить. Проверки бизнес-действий учитывают не только права объектов, но и текущего сотрудника, исполнителя, статус заявки и тип перехода.

## 10. Исключения из первоначальной модели

Без подтверждения не перенесены:

- приоритет «Критический»;
- табличная часть «Комментарии» документа «ITЗаявка»;
- статус «Просрочена»;
- множество отдельных отчётов;
- регистры накопления;
- бизнес-процессы и задачи;
- неподтверждённые реквизиты справочников и регистров.

После публикации выгрузки конфигурации документ необходимо дополнить точными именами объектов, реквизитов и типами данных.
