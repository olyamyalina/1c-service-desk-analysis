# 04. TO-BE процесс обработки IT-заявок

## 1. Назначение раздела

Данный раздел описывает целевой процесс обработки IT-заявок после внедрения системы «1С Service Desk».

TO-BE процесс нужен для описания того, как должна быть организована работа внутренней IT-службы после автоматизации: как создаются заявки, как назначаются исполнители, как контролируются статусы, сроки реакции и решения, как фиксируется история изменений и как руководитель получает данные для контроля.

## 2. Цель TO-BE процесса

Цель TO-BE процесса — устранить проблемы текущего AS-IS процесса за счёт внедрения единой системы регистрации, обработки и контроля IT-заявок.

Целевой процесс должен обеспечить:

1. централизованную регистрацию всех IT-заявок;
2. прозрачный жизненный цикл заявки;
3. назначение ответственного исполнителя;
4. контроль сроков реакции и решения по SLA;
5. хранение истории изменений;
6. связь заявки с оборудованием;
7. контроль просроченных заявок;
8. формирование отчётности для руководителя IT-отдела.

## 3. Участники TO-BE процесса

В целевом процессе участвуют следующие участники.

### 3.1. Сотрудник компании

Сотрудник является заявителем. Он создаёт IT-заявку в системе, описывает проблему, отслеживает статус обращения и подтверждает результат выполнения.

Основные действия сотрудника:

* создать IT-заявку;
* указать описание проблемы;
* выбрать категорию обращения;
* указать оборудование, если проблема связана с устройством;
* отслеживать статус заявки;
* предоставить уточнение по запросу исполнителя;
* подтвердить решение проблемы;
* отправить повторное обращение, если проблема не решена.

### 3.2. 1С Service Desk

1С Service Desk — информационная система, в которой регистрируются, обрабатываются и контролируются IT-заявки.

Основные функции системы:

* зарегистрировать заявку;
* присвоить заявке номер;
* зафиксировать дату и время создания;
* установить начальный статус;
* определить сроки реакции и решения;
* хранить историю изменений;
* связать заявку с заявителем, исполнителем, категорией и оборудованием;
* фиксировать нарушение SLA;
* предоставлять данные для отчётов.

### 3.3. Специалист IT-отдела

Специалист IT-отдела является исполнителем заявки. Он получает назначенные заявки, берёт их в работу, выполняет необходимые действия и фиксирует результат.

Основные действия специалиста:

* просматривать назначенные заявки;
* принять заявку в работу;
* анализировать проблему;
* запросить уточнение у сотрудника;
* выполнить действия по решению проблемы;
* указать результат выполнения;
* изменить статус заявки;
* указать связь с оборудованием при необходимости.

### 3.4. Руководитель IT-отдела

Руководитель IT-отдела контролирует работу специалистов, просроченные заявки, нарушения SLA и загрузку исполнителей.

Основные действия руководителя:

* просматривать все заявки;
* контролировать просроченные заявки;
* анализировать загрузку специалистов;
* отслеживать нарушения SLA;
* просматривать отчёты;
* принимать решения по перераспределению нагрузки;
* контролировать критические обращения.

### 3.5. Ответственный за оборудование

Ответственный за оборудование ведёт информацию об устройствах, которые используются сотрудниками компании.

Основные действия ответственного:

* вести список оборудования;
* фиксировать закрепление оборудования за сотрудниками;
* обновлять состояние оборудования;
* фиксировать ремонт оборудования;
* анализировать историю обращений по устройствам.

## 4. Основной сценарий TO-BE процесса

Основной сценарий целевого процесса выглядит следующим образом:

1. Сотрудник сталкивается с IT-проблемой.
2. Сотрудник создаёт IT-заявку в системе 1С Service Desk.
3. Система регистрирует заявку.
4. Система присваивает заявке номер и дату создания.
5. Система устанавливает начальный статус «Новая».
6. Сотрудник указывает категорию, описание проблемы и при необходимости оборудование.
7. Система определяет приоритет заявки.
8. Система рассчитывает срок реакции и срок решения по правилам SLA.
9. Заявке назначается исполнитель.
10. Система меняет статус заявки на «Назначена».
11. Исполнитель получает заявку.
12. Исполнитель берёт заявку в работу.
13. Система фиксирует факт реакции исполнителя.
14. Система меняет статус заявки на «В работе».
15. Исполнитель анализирует проблему.
16. Если информации недостаточно, исполнитель запрашивает уточнение у сотрудника.
17. Если информации достаточно, исполнитель выполняет действия по решению проблемы.
18. Исполнитель указывает результат выполнения.
19. Система меняет статус заявки на «Решена».
20. Сотрудник проверяет результат.
21. Если проблема решена, сотрудник подтверждает закрытие заявки.
22. Система меняет статус заявки на «Закрыта».
23. Если проблема не решена, сотрудник возвращает заявку в работу или создаёт повторное обращение.
24. Все изменения статусов фиксируются в истории заявки.

## 5. Альтернативные сценарии

### 5.1. Недостаточно информации по заявке

Если исполнитель не может обработать заявку из-за недостатка информации, он переводит заявку в статус «Ожидает уточнения».

После этого сотрудник получает запрос на уточнение и добавляет недостающую информацию. После получения уточнения исполнитель продолжает обработку заявки.

### 5.2. Заявка связана с оборудованием

Если проблема связана с конкретным устройством, в заявке указывается оборудование.

Система позволяет посмотреть информацию об оборудовании:

* тип устройства;
* модель;
* инвентарный номер;
* ответственного сотрудника;
* текущее состояние;
* историю обращений;
* историю ремонтов.

Если требуется ремонт, на основании заявки может быть создан документ «Ремонт оборудования».

### 5.3. Заявка просрочена

Если срок реакции или срок решения нарушен, система фиксирует нарушение SLA.

Такая заявка должна отображаться в отчёте по просроченным заявкам и быть доступной для контроля руководителю IT-отдела.

### 5.4. Проблема не решена после выполнения заявки

Если сотрудник проверил результат и проблема не решена, заявка не должна закрываться окончательно.

Возможны два варианта:

1. заявка возвращается в статус «В работе»;
2. создаётся повторное обращение, связанное с исходной заявкой.

Для MVP проекта основным вариантом считается возврат заявки в работу.

### 5.5. Критическая заявка

Если заявка имеет критический приоритет, она должна обрабатываться быстрее обычной заявки.

Для критической заявки устанавливаются сокращённые сроки реакции и решения. Также такая заявка должна быть видна руководителю IT-отдела для контроля.

## 6. Жизненный цикл заявки

В целевом процессе заявка проходит следующие статусы:

1. **Новая** — заявка создана сотрудником и зарегистрирована в системе.
2. **Назначена** — заявке назначен исполнитель.
3. **В работе** — исполнитель начал обработку заявки.
4. **Ожидает уточнения** — исполнитель запросил дополнительную информацию у сотрудника.
5. **Ожидает оборудование или запчасть** — выполнение заявки временно невозможно без оборудования или комплектующих.
6. **Решена** — исполнитель указал результат выполнения.
7. **Закрыта** — сотрудник подтвердил решение проблемы.
8. **Отменена** — заявка отменена.
9. **Просрочена** — срок реакции или решения нарушен.

## 7. Контроль SLA

В TO-BE процессе для заявок используется контроль SLA.

SLA определяет:

* допустимое время реакции;
* допустимое время решения;
* правила определения просрочки;
* приоритетность обработки обращений.

Пример правил SLA:

| Приоритет   |   Срок реакции |   Срок решения |
| ----------- | -------------: | -------------: |
| Критический |       15 минут |         4 часа |
| Высокий     |          1 час |        8 часов |
| Средний     |         4 часа |  2 рабочих дня |
| Низкий      | 1 рабочий день | 5 рабочих дней |

Срок реакции считается выполненным, когда исполнитель берёт заявку в работу.

Срок решения считается выполненным, когда заявка переводится в статус «Решена».

Если срок реакции или решения нарушен, система фиксирует нарушение SLA.

## 8. История изменения заявки

В целевом процессе все важные изменения по заявке должны сохраняться в истории.

В истории фиксируются:

* дата и время изменения;
* пользователь, выполнивший изменение;
* старый статус;
* новый статус;
* комментарий;
* исполнитель;
* причина изменения.

История нужна для контроля процесса, анализа спорных ситуаций, оценки сроков обработки и формирования отчётности.

## 9. Связь заявки с оборудованием

Если заявка связана с конкретным устройством, в системе указывается оборудование.

Это позволяет:

1. видеть, какие обращения были по конкретному устройству;
2. анализировать часто ломающуюся технику;
3. отслеживать историю ремонтов;
4. определять ответственного сотрудника;
5. связывать ремонт оборудования с исходной IT-заявкой.

## 10. Отчётность в TO-BE процессе

Целевой процесс должен обеспечивать формирование отчётов для руководителя IT-отдела.

Основные отчёты:

1. заявки по статусам;
2. просроченные заявки;
3. нарушения SLA;
4. загрузка исполнителей;
5. среднее время решения заявок;
6. заявки по категориям;
7. обращения по оборудованию;
8. история ремонтов оборудования.

## 11. Как TO-BE процесс решает проблемы AS-IS

| Проблема AS-IS                                  | Решение в TO-BE                                    |
| ----------------------------------------------- | -------------------------------------------------- |
| Заявки поступают через разные каналы и теряются | Все заявки регистрируются в 1С Service Desk        |
| Нет единого реестра обращений                   | Система хранит список всех заявок                  |
| Непонятно, кто отвечает за обращение            | У каждой заявки есть назначенный исполнитель       |
| Нет прозрачного статуса                         | У заявки есть жизненный цикл статусов              |
| Нет контроля сроков                             | Система рассчитывает сроки реакции и решения       |
| Нет контроля просрочек                          | Система фиксирует нарушения SLA                    |
| Нет истории изменений                           | Все изменения сохраняются в истории заявки         |
| Нет связи с оборудованием                       | Заявка может быть связана с конкретным устройством |
| Руководитель не видит загрузку специалистов     | Формируются отчёты по исполнителям и заявкам       |
| Нет аналитики по частым проблемам               | Формируются отчёты по категориям заявок            |

## 12. Вывод

TO-BE процесс описывает целевую модель обработки IT-заявок после внедрения 1С Service Desk.

В отличие от AS-IS процесса, целевой процесс предполагает централизованную регистрацию обращений, назначение исполнителей, контроль статусов, расчёт сроков реакции и решения, фиксацию истории изменений, связь заявок с оборудованием и формирование отчётности.

Данный раздел является основой для построения BPMN TO-BE диаграммы, формирования функциональных требований, проектирования ER-модели и описания объектов 1С.
